Measurements remain useful beyond the app. Standard GPX viewers can show the route and waypoints. Radiation-aware readers can also recover the measurement windows, recompute dose rates, and calculate confidence intervals from the stored counts and duration.

Namespace & structure

02

Use the standard GPX 1.1 namespace for geographic elements and the GeigerGPX namespace for radiation elements. The namespace URI identifies the vocabulary; it is not a schema download URL.

XML · namespace declaration
<gpx version="1.1" creator="GeigerGPX"
     xmlns="http://www.topografix.com/GPX/1/1"
     xmlns:rad="https://github.com/bocovp/GeigerGPX">
  <!-- Radiation elements live inside GPX extensions. -->
</gpx>
metadata/extensionsTrack summaries, detector name, calibration, and edit marker.
trk/trkseg/trkpt/extensionsA measurement window tied to averaged coordinates and its midpoint time.
wpt/extensionsA standalone measurement or a location bookmark, with its label in GPX name.

Match extensions by namespace URI https://github.com/bocovp/GeigerGPX and local tag name. The prefix rad is conventional; another prefix bound to the same URI is equivalent. XML names are case-sensitive; only the documented legacy aliases are accepted. All radiation tags belong inside extensions, not directly under gpx, trkpt, or wpt.

01

<rad:doserate>

Track pointWaypoint

The radiation level at a point

The mean dose rate for the measurement window represented by this point. It is a rate, not the accumulated dose. For calibrated data, doserate = counts / seconds / sensitivity.

Why it exists Keeps the calibrated, ready-to-display result alongside the underlying measurement, so viewers do not have to know the original detector settings.

Export & reader details

The track reader accepts legacy rad:doseRate too. It prefers a positive stored dose rate; otherwise, for a duration greater than 0.000001 s, it reconstructs the value from counts, seconds, and track sensitivity. The waypoint reader uses the stored value and does not perform this reconstruction.

Written: Always written at each track point and waypoint.

Serialization: 5 decimal places.

Value type
Decimal
Unit
µSv/h
XML · rad:doserate
<extensions>
  <rad:doserate>0.20000</rad:doserate>
  <rad:counts>120</rad:counts>
  <rad:seconds>60.000</rad:seconds>
</extensions>
02

<rad:counts>

Track metadataTrack pointWaypoint

Preserve the counting statistics

At a track point or waypoint, the number of detector counts collected during that point’s rad:seconds window. In track metadata, the sum of counts over all stored track points, including points with bad coordinates. Point counts use a 32-bit integer; the metadata sum uses a 64-bit integer.

Why it exists A dose rate alone cannot tell you how certain a measurement is. Keeping counts and duration lets you calculate a confidence interval for one window or pool a series of windows without averaging rounded rates.

Export & reader details

These are counts after the configured counts-per-beep multiplier, not necessarily the number of audio beeps. No multiplier tag is exported. Treat independent-count assumptions with care when a device emits one beep for several counts.

Written: Always written in track metadata and at each point / waypoint.

Serialization: Integer.

Value type
Non-negative integer
Unit
counts
XML · rad:counts
<!-- In trkpt/extensions or wpt/extensions -->
<rad:counts>120</rad:counts>

<!-- In metadata/extensions: sum of all points -->
<rad:counts>150</rad:counts>
03

<rad:seconds>

Track metadataTrack pointWaypoint

The measurement’s exposure time

At a point, the duration over which its counts were collected. In track metadata, the sum of these durations over all stored track points, including points with bad coordinates. A waypoint stores the duration of its standalone measurement.

Why it exists Makes count rate and uncertainty reproducible. Unequal windows can be combined as Σ counts / Σ seconds; the arithmetic mean of dose rates would give short windows too much weight.

Export & reader details

Use a positive duration for a usable measurement. Newly recorded track-point time is the midpoint of its window, so reconstruct boundaries as time ± seconds / 2. The first-to-last timestamp difference is not the metadata duration. Export rounds each duration and the metadata total independently, so their displayed sums may differ slightly.

Written: Always written in track metadata and at each point / waypoint.

Serialization: 3 decimal places.

Value type
Non-negative decimal
Unit
seconds
XML · rad:seconds
<!-- A 60-second window centred on 10:00:30 UTC -->
<time>2026-01-15T10:00:30Z</time>
<extensions>
  <rad:seconds>60.000</rad:seconds>
</extensions>
04

<rad:sensitivity>

Track metadata

Carry the detector calibration

The count rate, in counts per second, corresponding to a dose rate of 1 µSv/h. Divide count rate by this number to obtain dose rate. The exporter writes the literal attribute dimension="cps/uSv/h"; it means cps / (µSv/h).

Why it exists Makes a track portable across devices and app settings: a later reader can use the calibration saved with the measurement instead of today’s settings.

Export & reader details

The reader currently parses the positive number and does not inspect the dimension attribute. Missing or non-positive sensitivity falls back to 10.0 in the current app. Sensitivity 1.0 is also used for the app’s count-rate mode; the writer omits accumulated dose in this case. Waypoint exports have no sensitivity tag: the app infers it as (counts / seconds) / doserate when all three values are usable, otherwise defaults to 10.0.

Written: Always written in track metadata.

Serialization: Rounded to 6 decimal places; at least 1 decimal.

Value type
Positive decimal
Unit
cps / (µSv/h)
XML · rad:sensitivity
<rad:sensitivity dimension="cps/uSv/h">10.0</rad:sensitivity>
<!-- 2 cps / 10.0 = 0.2 µSv/h -->
05

<rad:dose>

Track metadata

The accumulated dose for a track

The estimated dose accumulated over the stored track points. The exporter calculates dose = total counts / sensitivity / 3600. The factor 3600 converts the hours in µSv/h to seconds.

Why it exists Provides a compact track-level exposure summary, including measurement windows recorded while GPS was unavailable.

Export & reader details

This value is based on total counts and the track calibration, rather than summing already rounded point dose rates. A small nonzero dose may round to 0.000. Absence in count-rate mode does not mean zero exposure. Cropped or split exports summarize only their retained points.

Written: Written only when track sensitivity is not exactly 1.0.

Serialization: 3 decimal places.

Value type
Non-negative decimal
Unit
µSv
XML · rad:dose
<!-- 150 counts / 10.0 / 3600 = 0.004166… µSv -->
<rad:dose>0.004</rad:dose>
06

<rad:pointcount>

Track metadata

A fast point-count summary

The number of stored trkpt elements in the exported track, including points flagged with bad coordinates. It is not the number of waypoints and not the number of radiation counts.

Why it exists Lets a track list show its size without loading every point. Metadata summaries also let the app read duration and distance quickly.

Export & reader details

The current writer emits one track with one segment. The track reader also accepts the older spelling rad:pointCount. Recompute this summary whenever the point list changes.

Written: Always written in track metadata.

Serialization: Integer.

Value type
Non-negative integer
Unit
track points
XML · rad:pointcount
<metadata>
  <extensions>
    <rad:pointcount>2</rad:pointcount>
  </extensions>
</metadata>
07

<rad:distance>

Track metadata

Distance along valid coordinates

The sum of geographic distances between successive valid track points, as calculated by Android’s Location.distanceBetween. Points flagged as having bad coordinates are skipped; the next valid point is connected to the previous valid point.

Why it exists Gives a quick geographic summary without letting synthetic or unreliable coordinates inflate track length.

Export & reader details

With fewer than two valid points, the distance is zero. This is distance along the recorded valid points; it does not reconstruct the actual route travelled during a GPS gap. Bad-coordinate points still contribute to radiation totals.

Written: Always written in track metadata.

Serialization: 3 decimal places.

Value type
Non-negative decimal
Unit
metres
XML · rad:distance
<rad:distance>0.000</rad:distance>
<!-- A stationary track can still contain measurements. -->
08

<rad:device>

Track metadataWaypoint

Identify the measurement device

The human-readable name of the selected radiation detector. Track exports store it once in metadata. Waypoint exports may store it directly in the waypoint’s extensions.

Why it exists Preserves measurement provenance when tracks or individual observations are shared.

Export & reader details

On waypoint export, the writer also requires counts > 0 before including a device name. It is a label, not a stable identifier or a calibration record. Escape XML-sensitive characters such as & as &amp;.

Written: Optional; emitted only for a nonblank device name.

Serialization: Text.

Value type
XML-escaped text
Unit
device name
XML · rad:device
<rad:device>RADEX RD1008</rad:device>
<!-- Example with an escaped ampersand -->
<rad:device>Counter &amp; probe</rad:device>
09

<rad:edited>

Track metadata

Mark an edited track

Signals that the track was saved through an editing operation, such as cropping, splitting, or flagging coordinates. The writer emits true when the edited flag is set; otherwise it omits the tag.

Why it exists Preserves a simple indication that a file has been modified, while keeping the usual GPX point structure.

Export & reader details

This is not an edit log: it stores no original values, author, timestamp, or operation. The reader treats case-insensitive true as edited and other values or absence as false. Metadata summaries are recomputed on export.

Written: Written only when the export is marked edited.

Serialization: Literal true.

Value type
Boolean marker
Unit
true
XML · rad:edited
<metadata>
  <extensions>
    <rad:edited>true</rad:edited>
  </extensions>
</metadata>

Complete examples

04

These are self-contained GPX documents. Copy a file or download it to try in a reader; all numbers are illustrative.

Track

Two adjacent windows of a stationary survey: 120 counts in 60 s, then 30 in 30 s. The retained track is marked edited. Total dose rounds to 0.004 µSv; identical coordinates give zero distance.

XML · complete track.gpx
<?xml version="1.0" encoding="UTF-8"?>
<gpx version="1.1" creator="GeigerGPX"
     xmlns="http://www.topografix.com/GPX/1/1"
     xmlns:rad="https://github.com/bocovp/GeigerGPX">
  <metadata>
    <extensions>
      <rad:pointcount>2</rad:pointcount>
      <rad:distance>0.000</rad:distance>
      <rad:counts>150</rad:counts>
      <rad:seconds>90.000</rad:seconds>
      <rad:dose>0.004</rad:dose>
      <rad:device>RADEX RD1008</rad:device>
      <rad:sensitivity dimension="cps/uSv/h">10.0</rad:sensitivity>
      <rad:edited>true</rad:edited>
    </extensions>
  </metadata>
  <trk>
    <trkseg>
      <trkpt lat="51.50070000" lon="-0.12460000">
        <time>2026-01-15T10:00:30Z</time>
        <extensions>
          <rad:doserate>0.20000</rad:doserate>
          <rad:counts>120</rad:counts>
          <rad:seconds>60.000</rad:seconds>
        </extensions>
      </trkpt>
      <trkpt lat="51.50070000" lon="-0.12460000">
        <time>2026-01-15T10:01:15Z</time>
        <extensions>
          <rad:doserate>0.10000</rad:doserate>
          <rad:counts>30</rad:counts>
          <rad:seconds>30.000</rad:seconds>
        </extensions>
      </trkpt>
    </trkseg>
  </trk>
</gpx>

Waypoints

A five-minute measurement and a location-only bookmark. Waypoints are exported in timestamp order. The second point’s zero duration indicates no measurement, not a measured zero radiation level. No device tag is written for it.

  <wpt lat="51.50070000" lon="-0.12460000">
    <time>2026-01-15T10:05:00Z</time>
    <name>Five-minute background measurement</name>
    <extensions>
      <rad:doserate>0.20000</rad:doserate>
      <rad:counts>600</rad:counts>
      <rad:seconds>300.000</rad:seconds>
      <rad:device>RADEX RD1008</rad:device>
    </extensions>
  </wpt>
  <wpt lat="51.50070000" lon="-0.12460000">
    <time>2026-01-15T10:06:00Z</time>
    <name>Location bookmark without a measurement</name>
    <extensions>
      <rad:doserate>0.00000</rad:doserate>

GPS gap

A measurement recorded without reliable GPS. The GPX fix value none flags the coordinates; this point still contributes counts, seconds, and dose to track totals. Synthetic or interpolated coordinates must not be treated as a measured position.

Counts make confidence possible.

05

A dose rate of 0.2 µSv/h might come from 2 counts in a second or 600 counts over five minutes. The rates match; their statistical uncertainty does not. This is why the format keeps both counts and exposure time.

One measurement window · T > 0, S > 0
count rate = N / T
dose rate = N / (T × S)
Several windows · same calibration
N = Σ counts; T = Σ seconds
pooled dose rate = N / (T × S)

The track example pools to 0.16667 µSv/h. Averaging its two rates would give 0.15000 µSv/h because it would weight a 30-second window as heavily as a 60-second window.

Mirrors the app’s fixed-window interval: tabulated χ² quantiles for shape ≤ 11 and a Wilson–Hilferty approximation above that. Demonstrates counting uncertainty only, with a constant, known calibration.

Reconstructing a 95% interval

For independent Poisson counts over a fixed observation window, use a two-sided interval with α = 0.05. Let χ²(p, ν) denote the p-quantile of a chi-square distribution with ν degrees of freedom:

lower cps = 0, if N = 0; otherwise χ²(0.025, 2N) / (2T)
upper cps = χ²(0.975, 2(N + 1)) / (2T)
dose-rate bounds = count-rate bounds / S

Zero detected counts over a positive duration still have a nonzero upper bound. A zero-duration bookmark cannot support an interval.

For a series, pool independent, non-overlapping windows with the same calibration. If rates vary along a route, the pooled estimate describes an exposure-time-weighted average, not the rate at each location. Separate data with different sensitivities before pooling. Count-triggered stopping rules or counts grouped by beeps can need a different statistical model; the app’s interval class also supports an event-at-end adjustment.

No confidence-interval tags are exported. Bounds are derived from counts, duration, calibration, and the chosen statistical model. This preserves the ability to choose another confidence level or recompute an interval after combining windows.

Reading & writing

07

These conventions describe the current implementation and help preserve both geographic and measurement data.

Keep the units explicit

Calibrated dose rates are in µSv/h, dose is in µSv, duration in seconds, and distance in metres. Write numbers with a period as the decimal separator and no thousands separators. Do not append unit text to numeric content. Sensitivity 1.0 can represent count-rate mode; the file has no separate per-point unit marker.

Preserve the GPX context

GPX lat and lon are decimal degrees, written to eight decimal places. Track coordinates are averaged over a measurement window when GPS samples are available. GPX time is written as an ISO 8601 UTC instant ending in Z when the timestamp is positive; track times represent window midpoints.

Handle missing data deliberately

The current reader defaults missing or malformed point counts and seconds to zero, and missing calibration to 10.0. These are application fallbacks, not proof that a measurement was zero. A positive stored track dose rate takes precedence over reconstruction; waypoint dose rates are not reconstructed on import.

Keep GPS quality separate from counts

Current exports flag bad track coordinates using <fix>none</fix>. The reader also recognizes legacy rad:badCoordinates. Bad points remain in count, duration, dose, and point-count summaries, but are skipped for distance and geographic measurement visualizations.

Recompute summaries after edits

Metadata is a summary of the stored point list, not an independent measurement. The exporter recalculates it after edits. For quick statistics, the app can use metadata distance and seconds before reading the points, so stale metadata can mislead a reader. Allow small differences caused by independent decimal rounding.

Understand the optional ele shortcut

An app setting can duplicate dose rate into GPX ele so basic viewers can plot it. In that mode, ele contains radiation data rather than elevation in metres. The rad:doserate value is still written; the GeigerGPX reader does not use ele as a radiation fallback. Consumers must interpret that shortcut deliberately.

Escape labels as XML

Device labels and waypoint names are text. Escape &, <, >, quotes, and apostrophes appropriately. Unknown extension elements are ignored by the current reader; consumers that rewrite GPX should preserve unfamiliar extensions whenever possible.

Use this as an implementation reference

This document describes current writer and reader behavior. There is no radiation XSD or separate extension-version attribute in the exporter. GPX version="1.1" versions GPX itself. A permissive app import does not replace validation of finite numeric values, meaningful durations, or GPX structure.

GPX element ordering. Complete examples above use the standard GPX element order. Current app exports place name before time in waypoints, and place ele after time when the shortcut is enabled. Strict GPX 1.1 schema validators can reject that ordering. A compatible writer should place ele before time and time before name.
